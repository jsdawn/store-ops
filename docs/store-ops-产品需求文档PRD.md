## 1. 产品背景与目标

### 1.1 背景

实体门店（美容美发、宠物、烘焙、足浴等服务业态）普遍依赖纸质会员卡或 Excel 记账，存在会员资产不清、充值赠送算不清、优惠核销靠人情、经营数据看不见四大痛点。市面成熟 SaaS（客如云、美团收银）面向大中型连锁，对小微商家偏重偏贵。

store-ops 定位为轻量级多租户门店经营 SaaS：平台方售卖系统使用权，商家（租户）注册后自建门店、自管员工，顾客通过微信小程序完成会员注册、积分兑换与余额查询，商家通过小程序完成收银与核销。

### 1.2 产品目标

| 目标 | 衡量方式 |
|---|---|
| 会员资产线上化 | 会员余额、积分、优惠券全部可在小程序查询，与门店台账一致 |
| 收银无纸化 | 店员用小程序开单收款，替代纸质小票 + 计算器 |
| 会员粘性闭环 | 消费攒积分 → 积分兑券 → 券再消费，形成复购回路 |
| 商家可自营活动 | 充值赠送（充 100 送 10）、满减/折扣券配置无需平台介入 |

### 1.3 本期核心价值主张

**记账式经营闭环**：不接线上支付，商家线下收款、系统记账确权。用最低的实现成本跑通「充值 → 消费 → 攒分 → 兑券 → 核销」完整会员经营链路。

## 2. 术语定义

| 术语 | 定义 |
|---|---|
| 租户（tenant） | 品牌方或单店商家，平台售卖系统使用权的最小单位。连锁店 = 1 租户 N 门店，单体店 = 1 租户 1 门店 |
| 门店（store） | 经营主体，会员/余额/积分/优惠券/订单全部挂在门店级（store_id），A 店会员在 B 店是陌生人 |
| 会员（member） | 顾客在某门店的会员身份。member ≠ sys_user，顾客走小程序独立登录（Sa-Token `mp` 端） |
| 会员余额（balance） | 顾客在门店的储值账户金额，由线下充值（本金 + 赠送）累积，消费时可扣减 |
| 充值赠送 | 线下充值促销活动，如充 100 送 10，会员实际到账 110 元 |
| 会员积分（point） | 消费金额按门店规则转化生成的虚拟权益，仅可兑换优惠券，不可抵扣现金、不可提现 |
| 优惠券（coupon） | 积分兑换获得的消费凭证，分满减券与折扣券，每笔订单限用一张 |
| 记账式收银 | 线下收款、系统记账：商家确认已实际收到钱（微信/支付宝/现金）后录入，不接线上支付通道 |
| 余额收款 | 用会员余额支付订单，系统直接扣减等额余额 |
| 核销 | 优惠券在收银时被使用并失效的过程 |
| 开单 | 店员在收银台创建一笔待收款订单的动作 |

## 3. 用户角色

| 角色 | 端 | 职责 | 数据范围 |
|---|---|---|---|
| 平台超管 | 管理台 | 开租户、设套餐与到期时间、停用续费 | 全平台 |
| 租户管理员 | 管理台 | 建门店、拉员工、配角色、看全租户报表 | 本租户全部门店 |
| 店长 | 管理台 + 小程序工作台 | 本店会员/订单/积分查询，员工管理 | 本店 |
| 店员/收银员 | 小程序工作台 | 开单收款、充值确认、核销优惠券 | 本店操作级 |
| 顾客 | 小程序顾客端 | 注册会员、查余额积分券、积分兑券 | 本人 |

小程序为双角色同端：底部 tabbar 固定顾客视角（首页/积分商城/我的），员工手机号绑定员工身份后「我的」页出现商家工作台入口。

## 4. 总体业务流程

```
【充值流程】
顾客到店 → 商家线下收款（微信/支付宝/现金）
→ 店员小程序录入：充值金额 + 赠送金额 + 充值方式 → 确认到账
→ 会员余额 +（充值金额 + 赠送金额），记充值流水

【消费流程】
顾客到店消费 → 店员小程序开单（选会员、录商品/服务明细）
→ 选优惠券（可选，每单限一张）→ 系统算出应付金额
→ 选支付方式（余额/微信/支付宝/现金）→ 确认收款
→ 余额收款：扣减会员等额余额；其余方式：仅记录支付方式
→ 订单完成 → 按券后实付金额生成积分 → 优惠券核销

【积分兑换流程】
顾客小程序积分商城 → 浏览可兑优惠券 → 支付积分兑换
→ 扣积分、发券至会员账户 → 下次消费收银时由商家选用核销
```

## 5. 功能需求

### 5.0 门店管理

**定位说明**：租户（sys_tenant）与租户套餐为框架内置能力（平台超管操作，见架构方案 6 节）；**门店不是框架内置实体**，为本期自研业务模块（ops-store，biz_store 表）。会员、余额、积分、优惠券、订单全部挂在门店级（store_id），门店是所有业务数据的最小归属单位。

**与 dept（部门）的关系——先建部门，再关联（定稿）**：

- RuoYi 数据权限按 dept 树过滤，dept 承担「组织架构 + 数据权限」职责，store 承担「经营主体」职责，两者分离、通过 `biz_store.dept_id` 关联
- 建店流程（租户管理员操作）：
  1. 框架「部门管理」建部门：租户总部（租户初始化自带）下新建门店部门（如「佛山禅城店」）
  2. 门店管理 → 新建门店，填写门店信息并**选择未绑定门店的部门**完成关联
  3. 框架「用户管理」把店长/店员挂到该门店部门下；店长角色的数据权限 = 本部门，即本店
- 约束：**1 个部门 ↔ 1 家门店**；门店表单的部门下拉仅列出本租户下未绑定任何门店的部门；**门店一经创建，绑定部门不可换绑**（业务表冗余 dept_id，换绑将导致历史数据归属漂移；建错部门走「停用旧店 + 新建」替代，换绑功能留待后续迭代）

**页面字段说明**（管理台 · 门店管理）：

| 字段 | 类型 | 必填 | 校验规则 |
|---|---|---|---|
| 门店名称 | 文本 | 是 | ≤ 20 字，租户内不重复 |
| 所属部门 | 下拉 | 是 | 仅显示本租户未绑定门店的部门；保存后写入 biz_store.dept_id |
| 门店地址 | 文本 | 否 | ≤ 50 字 |
| 状态 | 开关 | 是 | 启用 / 停用，默认启用 |
| 备注 | 文本 | 否 | ≤ 100 字 |
| 小程序码 | 列表操作 | - | 启用状态下可查看/下载；scene 携带 store_id，顾客扫码进店建档的唯一入口（见 5.1.1） |

列表列：门店名称、绑定部门、地址、状态、创建时间、操作（编辑 / 小程序码 / 停用·启用）。

**业务规则**：

- 权限：门店管理菜单仅授予租户管理员（平台超管管到租户级、不下沉门店；店长不开放本菜单）
- 店长不在此指定：门店管理只管经营主体，「谁当店长」= 员工挂部门 + 角色配置，走框架用户/角色管理
- 状态生命周期：仅 启用 ↔ 停用，**本期不提供删除门店**（会员/订单/券/流水均挂 store_id，删除需级联清理，列非本期范围）
- 停用影响：
  - 顾客端：扫该店小程序码提示「门店暂停营业」，不可建档、不可兑换该店券
  - 商家端：该店店员/店长登录工作台提示无可用门店，收银/充值/核销不可用
  - 数据：已有会员资产、订单、流水全部保留，重新启用后原样恢复
  - 管理台：租户管理员可正常查询该店历史数据（数据权限按部门树规则不变）
- 新建门店保存即生效：启用状态下小程序码立即可扫、可建档

### 5.1 会员体系

#### 5.1.1 会员档案

**业务规则**：

- 会员归属门店级（member.store_id），各店独立会员池
- **会员按门店 + 手机号唯一标识**：唯一约束 `(tenant_id, store_id, mobile)`，手机号为建档必填字段；同一手机号在 A、B 两店是两个独立会员
- open_id 仅作微信登录凭证，不作唯一标识；一个会员档案最多绑定一个 open_id，补绑后自动更新
- 顾客扫门店小程序码 → 微信授权登录 → 首次进入需确认手机号 → 按 (门店, 手机号) 匹配：已有档案（线下登记过）则补绑 open_id 并登录，无档案则新建
- 线下登记会员（无微信）：店员录入手机号建档，open_id 为空；顾客日后微信登录同手机号时自动合并到同一档案，不产生重复会员
- 会员字段含余额（balance）、积分（point_balance），均以门店为账户主体

**页面字段说明**（小程序顾客端 · 我的）：

| 字段 | 说明 |
|---|---|
| 当前门店 | 默认按最近一次扫码/消费的门店自动切换；顾客可在门店列表手动切换（列表仅展示已注册过会员的门店，按最近消费排序），新门店通过扫该店小程序码进入 |
| 会员卡号 | 系统生成，门店内唯一 |
| 余额 | 当前可用余额，单位元，两位小数 |
| 积分 | 当前可用积分，与余额同格式：两位小数，单位分值 |
| 优惠券 | 张数入口，点击进券列表 |

**页面字段说明**（小程序工作台 · 会员查询）：

| 字段 | 说明 |
|---|---|
| 搜索 | 手机号 / 卡号 / 微信昵称模糊搜索，仅本店会员 |
| 会员列表项 | 昵称、手机号、余额、积分、开卡时间、累计消费 |

#### 5.1.2 会员余额与充值

**业务流程**：

1. 顾客到店表达充值意向，商家告知充值活动（如充 100 送 10）
2. 商家通过个人微信/支付宝/现金收取款项（**平台不经手资金，不接线上支付**）
3. 店员在小程序工作台 → 会员详情 → 充值，录入下方字段，确认到账
4. 系统入账：余额 += 充值金额 + 赠送金额，记充值流水

**页面字段说明**（小程序工作台 · 充值录入）：

| 字段 | 类型 | 必填 | 校验规则 |
|---|---|---|---|
| 会员 | 选择 | 是 | 搜索选定，仅本店会员 |
| 充值金额（本金） | 金额 | 是 | > 0，两位小数，上限 99999.99 |
| 赠送金额 | 金额 | 否 | ≥ 0，默认 0；无活动时不填 |
| 充值方式 | 单选 | 是 | 微信收款 / 支付宝收款 / 现金收款 |
| 到账合计 | 只读 | - | 充值金额 + 赠送金额，实时计算展示 |
| 备注 | 文本 | 否 | ≤ 100 字，如「周年庆活动」 |

**业务规则**：

- 充值方式仅作记录，标记商家实际线下收款渠道，不触发任何线上支付动作
- 本金与赠送金额合并入同一余额账户，消费时不区分扣减顺序（简化模型，MVP 不拆本金/赠送两个桶）
- 赠送金额必须 ≤ 充值金额（本金）
- 每笔充值记一条流水（recharge_log）：会员、充值金额、赠送金额、充值方式、操作店员、时间
- 充值确认后即时生效，**不支持撤销**；录错可在管理台发起负向冲正（需备注原因，记冲正流水）——冲正仅限当日。冲正入口仅管理台（小程序工作台无冲正），权限按 RuoYi 菜单权限授予，有冲正权限的角色即可操作，无需租户管理员审批
- 余额不可提现、不可跨店使用、不可转赠

#### 5.1.3 会员积分

**业务规则**：

- 积分来源（本期）：消费转化。订单完成时，按**券后实付金额**生成积分
- 转化规则为系统固定默认：`积分 = 券后实付金额 × 1`（**等额转化，消费多少转化多少**），本期不做门店级配置
- 积分与余额同格式：保留两位小数、不取整。实付 9.90 元 → 得 9.90 积分
- 积分用途（本期）：仅兑换优惠券。不可抵扣现金、不可转赠
- 积分采用余额 + 流水模式（point_log），每笔变动关联业务单号
- 已收款订单不产生积分回退（见 6.5）

**规则配置说明**：攒分规则本期为系统固定默认（等额转化、全店生效），管理台不提供积分规则配置页面，无需积分规则表；后续如需按门店/活动调整转化率，再迭代开放配置。

### 5.2 积分兑换（优惠券）

#### 5.2.1 优惠券类型与配置

**券类型（本期仅两种）**：

| 类型 | 说明 | 示例 |
|---|---|---|
| 满减券 | 订单满 threshold 元减 value 元 | 满 100 减 20 |
| 折扣券 | 订单按 discount 折优惠，最高减免 cap 元 | 8 折，最多优惠 50 元 |

**页面字段说明**（管理台 · 优惠券配置）：

| 字段 | 类型 | 必填 | 校验规则 |
|---|---|---|---|
| 券名称 | 文本 | 是 | ≤ 20 字 |
| 券类型 | 单选 | 是 | 满减券 / 折扣券 |
| 使用门槛 threshold | 金额 | 满减券必填 | > 0；折扣券不填（无门槛） |
| 优惠面额 value | 金额 | 满减券必填 | > 0 且 < threshold |
| 折扣率 discount | 百分比 | 折扣券必填 | 1–99（对应 1 折–9.9 折，精确到 0.1 折） |
| 折扣封顶 cap | 金额 | 折扣券选填 | ≥ 0，0 = 不封顶 |
| 兑换所需积分 | 数值 | 是 | > 0，两位小数（与积分格式一致） |
| 发行总量 | 整数 | 是 | > 0，兑换数量达上限后下架 |
| 每人限兑 | 整数 | 是 | ≥ 1 |
| 有效期 | 时间 | 是 | 兑换后 N 天内有效（自兑换时刻起算） |
| 状态 | 开关 | 是 | 上架 / 下架；下架后积分商城不可见，已兑换的不受影响 |

**业务规则**：

- 优惠券为门店级资产：各店独立配置、独立发行，A 店的券不能在 B 店用
- 券模板与券实例分离：模板是商家配置的「货架商品」，实例是顾客兑换后持有的券（记 member_id、store_id、来源模板、到期时间、状态）
- 券实例状态机：`未使用 → 已使用（核销）`、`未使用 → 已过期`；状态变更不可逆

#### 5.2.2 积分兑换流程（顾客端）

**业务流程**：

1. 顾客进入小程序 → 积分商城 tab → 展示当前门店在架券（含所需积分、有效期说明）
2. 点击券 → 确认兑换 → 校验积分充足、未超每人限兑、未售罄
3. 扣减积分、生成券实例，记积分消耗流水（关联券实例 ID）
4. 券进入「我的 → 优惠券」列表，倒计时展示有效期

**页面字段说明**（小程序顾客端 · 积分商城）：

| 字段 | 说明 |
|---|---|
| 我的积分 | 当前门店积分余额 |
| 券卡片 | 券名、类型标签（满减/折扣）、优惠内容大字、所需积分、剩余可兑数量 |
| 兑换按钮 | 积分不足时置灰并提示差额 |
| 我的优惠券列表 | 券面信息、状态（未使用/已使用/已过期）、到期时间 |

**业务规则**：

- 兑换即时扣积分，**不支持退券回积分**（兑换前二次确认弹窗提示）
- 有效期到期由系统定时任务批量置为已过期，过期不可再使用、不退积分
- 售罄 / 下架 / 限兑已达的券在商城不展示或置灰

#### 5.2.3 优惠券核销规则（收银时使用）

**核心链路：顾客端兑换 → 商家端收银时选用 → 订单完成即核销。**

- 收银开单选定会员后，系统自动拉取该会员在本店的**未使用且未过期**优惠券，供店员选择
- **每笔订单限用一张优惠券**，界面为单选，选定一张后其他券不可再选
- 可用性校验（选券时实时判断）：
  - 满减券：订单总额（券前）≥ threshold 才可选，否则置灰并提示门槛
  - 折扣券：无门槛；优惠额 = 订单总额 × (1 - discount/100)，超过 cap 按 cap 计
  - 券的 store_id 必须等于当前收银门店
- 优惠计算顺序：**先券后付**。应付金额 = 订单总额 − 优惠券优惠额；**不存在 0 元单**：应付金额必须大于 0 才可确认收款，优惠券不可将订单全额覆盖（配置校验已保证：满减券面额 < 门槛 ≤ 总额、折扣券最低 1 折，应付恒 > 0）
- 核销时机：店员点击「确认收款」且订单完成后，券实例置为已使用，记核销时间与关联订单号
- 订单作废（未收款）不涉及核销；已核销券不因任何原因恢复（见 6.5）

### 5.3 收银管理

#### 5.3.1 开单与收款流程

**业务流程**：

1. 顾客到店消费，店员在小程序工作台 → 收银开单
2. 选会员（可跳过，散客直接开单，散客无余额/积分/券）
3. 逐笔录入消费明细（单价 + 数量，名称选填），系统自动合计订单总额
4. 选优惠券（可选，每单限一张，见 5.2.3）
5. 选支付方式：**余额收款 / 微信收款 / 支付宝收款 / 现金收款**
6. 点击「确认收款」→ 订单完成，执行对应记账动作

**支付方式语义**：

| 支付方式 | 系统动作 |
|---|---|
| 余额收款 | 校验余额 ≥ 应付金额 → 扣减会员等额余额，记余额消费流水 |
| 微信收款 | 仅记录支付方式，标记商家已通过个人微信线下收款 |
| 支付宝收款 | 仅记录支付方式，标记商家已通过个人支付宝线下收款 |
| 现金收款 | 仅记录支付方式，标记商家已收取现金 |

后三种统称**线下收款标记**：平台不经手资金、不校验是否真实收到钱，收款真实性由商家自行负责。选择余额收款以外的会员，照样正常攒积分（按实付金额）。

**页面字段说明**（小程序工作台 · 收银开单）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 会员 | 选择 | 否 | 搜索本店会员；散客可跳过 |
| 消费明细 | 列表 | 是 | 逐笔录入：单价 + 数量（数量默认 1），名称选填；每笔自动算行金额（单价 × 数量），支持连续录入多笔（如 10 元 × 2、27 元 × 1），可增删改行 |
| 订单总额 | 只读 | - | 全部明细行金额自动合计，店员无需手工计算 |
| 优惠券 | 单选 | 否 | 基于订单总额判定可用性；展示该会员可用券，不可用券置灰并标注原因；选定后显示优惠额 |
| 应付金额 | 只读 | - | 订单总额 − 优惠额，自动计算 |
| 支付方式 | 单选 | 是 | 余额收款（余额不足置灰）/ 微信收款 / 支付宝收款 / 现金收款 |
| 本单积分 | 只读 | - | 按应付金额等额预估（1:1），下单后落账 |

**开单交互说明**：收银为「逐笔累加 → 合并结算」模式——店员按顾客实际购买逐笔录入单价与数量（例：10 元商品 × 2、27 元商品 × 1），系统实时合计出订单总额，再进入优惠券与收款环节；全部金额计算（行小计、总额、优惠额、应付）由系统完成，店员只录入不计算。本期无商品库，单价由店员手动输入（参考真实商品价目），名称仅作展示备注可留空。

**业务规则**：

- 订单号：雪花 ID 生成 + `order_no` 数据库唯一约束
- 防重复提交：前端按钮置灰 + 后端幂等 token（Redis），同一 token 只落一笔订单
- 余额收款与余额扣减在同一事务：扣余额失败则整单失败，不允许「订单成功但余额没扣」
- 余额不足时余额收款选项置灰，提示「余额 X 元，应付 Y 元」
- **不存在 0 元单**：应付金额必须大于 0 才可确认收款，必须有实际消费金额，券不可全额覆盖订单
- 订单完成即等额产生积分，积分流水关联 order_no
- 订单状态机：`待收款 → 已完成`；待收款订单可作废（见 6.5），已收款订单不可作废、不可退款（本期）

#### 5.3.2 订单查询

**页面字段说明**（小程序工作台 · 今日流水 / 管理台 · 订单列表）：

| 字段 | 说明 |
|---|---|
| 订单号 / 时间 / 门店 | 基础信息 |
| 会员 | 散客显示「散客」 |
| 订单总额 / 优惠额 / 应付金额 | 三段金额，优惠额展示所用券 |
| 支付方式 | 余额 / 微信 / 支付宝 / 现金 |
| 状态 | 待收款 / 已完成 / 已作废 |
| 本单积分 | 产生（+N） |

管理台订单列表按数据权限过滤：店长看本店，租户管理员看全部门店。

## 6. 边界与异常情况说明

### 6.1 会员与跨店

| 场景 | 处理 |
|---|---|
| A 店会员到 B 店消费 | 视为 B 店陌生人：查不到会员、余额/积分/券均不可用；需在 B 店重新注册 |
| 顾客扫码切换门店 | 「当前店」按最近扫码/消费切换，各店余额积分独立展示，不合并 |
| 同手机号在多店注册 | 允许，各店独立会员记录（唯一约束含 store_id） |
| 店员录入会员手机号重复 | 提示「该手机号已是本店会员」，跳转已有档案 |
| 顾客进入未注册的新门店 | 唯一途径是扫该店小程序码（门店列表不展示未注册门店）；扫码后首次使用会员能力（查余额/兑券）时确认手机号，按 (门店, 手机号) 建档 |
| 顾客微信登录填的手机号与线下档案不一致 | 按填写的手机号匹配/新建；同一顾客两部手机号会形成两个会员档案，本期不支持合并（合并功能列非本期边界） |

### 6.2 充值异常

| 场景 | 处理 |
|---|---|
| 商家实际未收到钱但已确认到账 | 系统无法感知（记账式固有边界）；录错由有冲正权限的员工当日冲正，记冲正流水与原因 |
| 赠送金额录入超过本金 | 前端拦截 + 后端校验拒绝（赠送 ≤ 充值金额） |
| 充值确认时会员正在消费 | 余额扣减依赖数据库行级锁 / 乐观锁，串行生效，不出现超扣 |

### 6.3 余额并发

- 余额收款与充值确认可能并发，余额账户更新采用行锁（SELECT ... FOR UPDATE）或乐观锁版本号，保证扣减金额准确、不扣成负数
- 同一会员并发多笔余额收款：逐笔校验余额充足，不足的订单失败并提示

### 6.4 优惠券异常

| 场景 | 处理 |
|---|---|
| 选券后、确认收款前券刚好过期 | 确认收款时二次校验券状态，过期则拦截并提示重选 |
| 券门槛校验前后订单金额变化（改明细） | 每次明细变动后重新校验已选券，不满足则自动取消选中并提示 |
| 兑换时积分被并发消耗（两台设备同时兑换） | 积分扣减原子操作，不足的一方失败 |
| 券模板下架 | 商城不可见；已持有券正常使用至过期 |

### 6.5 订单异常

| 场景 | 处理 |
|---|---|
| 开单后顾客不买了 | 待收款订单可作废，不产生余额/积分/券变动 |
| 已收款订单要求退款 | **本期不支持退款**。余额收款错账由有冲正权限的员工当日冲正（负向余额流水），微信/支付宝/现金错账由商家线下自行处理，系统仅支持在订单上追加备注 |
| 订单作废是否回退积分 | 待收款作废不产生过积分，无回退问题；已收款订单不可作废 |
| 重复点击确认收款 | 幂等 token 拦截，同 token 仅一笔有效 |
| 券已核销但订单又出问题 | 已核销券不恢复（简化规则，避免状态回滚复杂度）；金额层面按上条处理 |

### 6.6 权限与安全边界

- 顾客接口（/mp/**）走自定义鉴权，**手动校验** member 的 store_id / tenant_id 归属，禁止依赖框架数据权限
- 顾客仅能查看/操作本人会员资产；店员仅能操作本店会员；跨店访问返回无权限
- 充值冲正仅管理台可操作，按 RuoYi 菜单权限授予（有权限即可，不限店长）；券模板配置限店长及以上角色
- 金额与积分均以「分」为最小单位存储与计算（两位小数精度），展示层转元（两位小数），避免浮点误差
